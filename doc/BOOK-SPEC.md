# 任务提示词：编写《Blender 开发指南》（正式、全面、系统）

> 使用方式：把本文件内容（或本文件）作为任务描述交给 DSH，让它产出全书。
> 本提示词已尽量自包含；如会话环境已有克隆好的源码，可省去重复克隆。

---

## 一、任务概述

编写一本 **正式、全面、系统** 的 Blender 开发指南（书），面向有 C/C++ 或 Python 基础的开发者，帮助读者从零掌握两件核心能力：

1. **Python 插件开发**（不碰 C++ 源码也能扩展 Blender）；
2. **基于 Blender 源码进行修改**（改 C++ 源码、加功能、提速、加编辑器/修饰器/节点等）。

这本书不是“快速上手小抄”，而是 **成体系的正式读物**：概念由浅入深、章节编排合理、必要时用图表形象说明、关键概念允许用好几页的 section 展开讲透。

---

## 二、交付物与形式

- **语言**：中文正文，代码/命令/术语保留英文原文。
- **排版**：使用 Typst（允许第三方包，例如 `cetz` 画图、`codelst` 列代码等）。最终交付 **可编译的 Typst 源码 + 一份 PDF**。
- **源码组织**：全书可拆成多个 `.typ` 文件（如每章一个文件）分别编写，由主文件统一 `#include`，最终编译为 **一本 PDF**；共享的样式/图表辅助函数放公共模块（如 `common.typ`）。
- **图表**：用 Typst 图表包（推荐 `cetz`）绘制；至少覆盖下方「九、必备图表」列出的图。
- **插图与截图**：界面/操作类插图用 **编译成功的 Blender** 实机截图；截图宽高不超过 1920×1080，优先只截局部区域（相关窗口/面板/菜单）。
- **篇幅**：全面系统，不做硬性页数限制；以“把该讲的概念讲透、案例能跟着做”为准（粗略参考：正文 150–250 页量级，最终以内容完整性为准，宁全勿缺）。
- **配套源码**：正文所有代码片段、命令、路径都要 **对照真实源码核对过**（见「七、技术与环境约定」），不允许凭印象编造 API 或字段名。

## 三、目标读者与定位

- 读者：会 C++（能读懂类、继承、模板、`std::` 容器、CMake 基本用法）和 Python（函数/类/装饰器/模块）；没读过 Blender 源码。
- 定位：从“读得懂”到“改得动”，再到“能贡献”。既是一本教程，也是一本可常翻的参考手册（附录给出术语表、路径索引、命令速查）。
- 覆盖平台：**Windows、macOS、Linux 三平台** 的构建与开发环境搭建都要写；正文若以某一平台为主示例，需在相应章节给出其余平台的差异说明。

**第 0 章　导论**
- 0.1 本书定位、读者、学习路线（配路线图）

- 0.3 🔶 开发边界与思路：先想清楚“能做 / 不能做”再动手（配一张边界对照表）
  - 插件（addon）只能用 Python 开发；Blender 没有 C++ 插件 API，官方也明确不打算加

## 六、构建方式与 CMake 的讲解要求

- **三平台都要覆盖**：Windows（Visual Studio / MSYS2）、macOS（Xcode CLT + Homebrew）、Linux（发行版包管理器）。每章给出该平台的完整“从零到跑起来”步骤，并标注三平台差异。
- **CMake 等必要工具可“稍提”但讲清楚**：不需要写成 CMake 专著，但要讲清读者实际会用到的部分——目标/生成器/构建目录/缓存/常用配置项/`BUILD_DIR`/多配置与单配置生成器的区别/如何生成 IDE 工程。控制在“够用”范围。
- **依赖获取**：明确当前版本（以实际克隆到的分支为准）预编译库是 **Git LFS 子模块** 还是 svn——以源码里的 `.gitmodules` 和 `build_files/utils/make_update.py` 为准，不要照搬旧资料。
- **不许 hack**：缺工具用官方途径安装（macOS 用 Homebrew、Linux 用包管理器、Windows 用官方安装包/包管理器），不要用“绕过 SSL 校验/跳过依赖/改奇怪配置”让代码勉强编译。

## 七、技术与环境约定（给 DSH 的执行要求）

1. **先拉源码并编译成功**：编写文档前，先按 `book/blender-baseline.json` 指定的版本、分支与 commit，把 Blender 源码克隆到任意本地目录，并 **编译出可运行的 Blender**（后续截图与核对都基于它）。所有正文引用的 **文件路径、结构体字段、函数签名、命令、构建产物路径** 都要在源码里核实后再写入；正文不得假设读者采用了书稿工程内部的目录名。
2. **工具要就绪**：缺少命令行工具（git-lfs、cmake、ninja、编译器、typst 等）时，可 **要求开发者安装**，或 **AI 用官方方式自动安装**（macOS 用 `brew`、Linux 用包管理器、Windows 用官方安装包）。禁止用“关闭校验 / 跳过依赖 / 改奇怪配置”等方式勉强编译成功；记录实际安装命令。
3. **代码片段要可验证**：关键 C++/Python 示例应尽量与源码一致或可编译可运行；不能确定处要明确标注“示意/节选”。
4. **多平台部分**：DSH 本身在某一个平台执行，Windows/Linux 的构建步骤可以依据官方文档与源码 `build_files/` 描述，但要准确，不能编造命令。
5. **用编译成功的 Blender 截图**：界面/操作类插图优先用编译出的 Blender 实机截图；截图宽高不超过 1920×1080，能只截 **局部区域**（相关窗口/面板/菜单）就只截局部，不要整屏。
6. **交付前自检**：用 `typst compile` 通过、PDF 生成、字体（中文）正确嵌入、图表与截图渲染正常、目录/编号无重复。

## 十一、作者备注（本次会话沉淀的经验，供后续 DSH 参考，避免重复踩坑）

- Blender 较新版本（5.x）预编译库是 **Git LFS 子模块**（`lib/<平台>_<架构>`），`make update` 用 git-lfs 而非 svn；构建产物默认在源码目录 **上一级**（`../build_<OS>`）。
- Typst 写作坑：正文里带尾下划线的标识符（如 `ED_`、`BKE_`）会触发“未闭合强调”，需放入行内代码 `` `ED_` ``；`#table(...)` 要用 `)` 闭合，不要误写成 `]`；cetz 里 `长度 - 长度` 在函数实参内联会解析失败，先 `let` 预计算；中文用系统字体（如 PingFang SC）+ 等宽字体（Menlo）。
- 章节编号与正文交叉引用（“见第 X 章”）要一致，别出现“自动编号 + 手写编号”双重编号。
- 涉及具体 API 时先 `grep`/`read` 源码，不要凭记忆写。
